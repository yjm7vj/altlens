### Metric Calculation Implementation

Implemented a `CashFlow` dataclass to represent fund cash-flow events:

- `event_date`
- `amount_usd`
- `flow_type`

Implemented `calculate_moic`, which computes:

```text
total distributions / total paid-in capital
```

Capital calls are treated as invested capital. Distributions are treated as returned capital. If there is no invested capital, the function returns `0.0`.

Implemented `calculate_irr`, using XIRR-style logic for irregular real-world fund cash-flow dates.

The IRR calculation:

1. sorts cash flows chronologically
2. converts event dates into year fractions from the first cash-flow date
3. checks that cash flows include both negative and positive values
4. solves for the discount rate that makes net present value equal zero
5. returns `0.0` when a valid IRR cannot be solved

The implementation uses SciPy's `brentq` root solver. This follows the build plan's recommendation to use a proven numerical method instead of relying on a fragile custom Newton-method implementation.

### Development Challenges

#### Dependency Setup

The first test run failed because `pytest` was not installed in the local Python environment. Installing all development dependencies at once took longer than expected because scientific Python packages were involved. Installing `pytest` separately after SciPy was available resolved the immediate test blocker.

This matters for future development because setup should stay simple and documented. If dependency installation becomes slow or unreliable, the project may need pinned versions or a more explicit virtual-environment workflow.

#### IRR Test Calibration

One multiple-capital-call IRR test initially used an incorrect expected value. The solver returned approximately 15.34%, while the first estimate expected approximately 17.5%.

After reviewing the cash-flow timing, the solver result was correct for:

- `-100` on 2020-01-01
- `-50` on 2021-01-01
- `+220` on 2023-01-01

The expected value was corrected to approximately 15.3%.

This is an important development lesson for AltLens: IRR is sensitive to timing, and intuitive estimates can be misleading. Metric tests should continue to use independently checked examples whenever new financial calculations are added.

## 2026-07-24

### Product Direction Expanded Toward AI Research Briefs

AltLens' direction was expanded from a basic dashboard with an AI search bar into a more distinctive alternative-investment research agent.

The product should take inspiration from public-market financial research agents, but avoid becoming a generic stock-market or Bloomberg-style clone. Its unique focus should be private-market and alternative-investment workflows:

- fund and manager comparison
- vintage-year analysis
- cash-flow based performance metrics
- portfolio-company exposure
- sector and theme research
- diligence memo generation
- source-backed assumptions
- clear labels for verified, estimated, and illustrative data

Added `PRODUCT_DIRECTION.md` to capture this strategy.

### Important Development Decision

The AI output should eventually be a structured research brief instead of a loose chat answer.

Research briefs should include:

- executive summary
- key metrics
- supporting tables
- charts
- cited sources
- assumptions
- data quality notes
- follow-up questions

This affects future backend and frontend design because API responses should support structured content, not only plain text.

### Agent Architecture Direction

The AI layer should continue to use constrained backend tools instead of unrestricted SQL generation.

Future tools may include:

- `get_fund_profile`
- `get_fund_metrics`
- `compare_funds`
- `get_top_performers`
- `get_vintage_year_summary`
- `get_sector_exposure`
- `generate_research_brief`
- `explain_metric_methodology`

This keeps the product safer and more verifiable, especially because financial data can be incomplete or sensitive.

### Local Model Direction

AltLens should eventually support both hosted and local model providers.

Planned direction:

1. implement a provider interface
2. support OpenAI first
3. add Ollama after the tool layer is stable
4. expose model selection without assuming every model can handle every research workflow

This matters because local models are useful for sensitive research material, but smaller models may struggle with multi-step financial tool use.
